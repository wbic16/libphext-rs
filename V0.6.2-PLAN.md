# libphext v0.6.2 — plan

Source of the requirements: the Holostore round-2 re-implementation
(wbic16/holostore, PHEXT.md), which re-implemented a consensus KV store's
storage core phext-natively and recorded six places where phext or
libphext made the work harder than the problem. This release remediates
each one **simply**: no new dependencies (xxh3 is already the crate's
checksum; base64 is already the `binary` feature's dependency), no new
subsystems, and an explicit verdict where the library layer cannot own
the problem.

Will's rule for this work: assume any failure to integrate phext is due
to the integrator's priors, and retry three times before calling a
phext limitation. Two of the six items shrank under that rule (items 5
and 6 were smaller than first reported); two are genuinely bounded
(items 3 and 4).

## The list

### 1. Append writer — SOLVED
`append` / `append_batch` / `append_checked` in `phext.rs`, built on the
existing private `append_scroll` delimiter emitter. Appending at a
coordinate after the document's end returns the input plus exactly a
delimiter run and the new content, so a host writes only the suffix and
syncs once. Out-of-order targets and empty scrolls return `None`.
Tests: exact landing, rejection cases, trailing-break inputs,
volume-boundary appends, batch ordering.

### 2. Per-scroll integrity — SOLVED (for accidental corruption)
`checked_scroll` / `verify_checked_scroll` / `uncheck_scroll` /
`fetch_checked`: a scroll may carry a final trailer line
`phext-check:xxh3-128:<checksum>` using the existing `checksum`
function. Torn writes and bit corruption fail verification; recovery
treats an unverifying scroll as uncommitted. Limit, stated plainly:
xxh3 is not cryptographic — this detects accidents, it does not
authenticate. Tests: round-trip, tamper, torn tail, marker-shaped
payload lines, checked vs plain vs missing fetches.

### 3. Atomic multi-scroll writes — PARTIALLY SOLVED; true atomicity UNSOLVABLE in libphext
`append_batch` constructs a whole batch as one suffix (one host write),
and `commit_scroll` / `verify_commit` add a marker scroll binding the
batch's count and content checksum, so a batch torn by a crash is
*detectable and rejectable* at recovery. Whether the write itself lands
atomically is the host filesystem's property — no string library can
own it, and v0.6.2 does not pretend to. Tests: verify, torn marker,
tampered entry, wrong batch size.

### 4. Durability contract — SOLVED as specification; code UNSOLVABLE by design
libphext performs no file I/O, so durability cannot be code here. The
crate docs (`src/lib.rs`) and readme now carry the whole profile in one
place: temp-file + write + sync + rename + directory-sync for rewrites;
single suffix write + sync before acknowledgment for appends; recovery
trusts only validated scrolls/commits and truncates after the last
valid one. Every phext host previously re-derived these rules
privately; one of the round-2 bugs (directory sync on a bare relative
path) lived exactly in that gap.

### 5. Empty-scroll semantics — SOLVED
The definition says a scroll exists iff it holds at least one byte.
`implode`'s serializer skipped empty values but its coordinate
tracking still advanced past them without emitting breaks, misplacing
every later scroll — and `explode` materialized delimiter runs as
empty map entries. Both are fixed: `dephokenize` advances its tracked
coordinate only when bytes were emitted, and `explode` filters empty
scrolls. (The implode half was found by this release's round-trip test,
not by reading: the defect only appears at the boundary.) `phokenize` is unchanged on purpose: it is the tokenizer
and reports positioned slots; existence semantics live in `explode`.
Tests: volume-jump documents explode to exactly their real scrolls;
implode with an empty value omits it; sparse round-trips hold.

### 6. Binary values inside line-structured scrolls — SOLVED by convention; the overhead is UNSOLVABLE
`binary::encode_field` / `decode_field` (feature `binary`, no new
dependency): one standard single-line armour, `phext-field:base64:` +
RFC 4648 base64, safe inside any `name=value` line grammar. What no
release can remove is the +33% base64 expansion — armouring arbitrary
bytes inside a text line costs that by construction. Tests: arbitrary
bytes (break bytes, NUL, 1 KiB pattern) round-trip on one line; plain
text and malformed bodies are rejected.

## Explicit non-goals
- No file I/O, no storage engine, no locking, no async.
- No new dependencies; no new format bytes; checked scrolls and commit
  markers are content conventions inside ordinary scrolls.
- No changes to `phokenize`, chains, addressing (0.6.1), or the seal.
- Ports (cs/cpp/C/py/node/java/kotlin/swift) are follow-on work after
  Will reviews this list; the rs implementation is the spec they port.

## Acceptance
`cargo test` and `cargo test --all-features` green: the 85/100-test
v0.6.1 baseline plus the new v0.6.2 suite in `src/test_v062.rs`.
